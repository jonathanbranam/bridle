Part of onboarding data-contracts (docs/context/onboarding-data-contracts.md §3, §7 step 2;
go-ahead from the orchestrator/human 2026-09-28) and meta-notes
(docs/questions/open/onboarding-survey-meta-notes-ajqa.md, go-ahead 2026-09-28). data-contracts
is the first Python project bridle onboards, meta-notes the second; both need an L2 pack
(docs/design/workflow-layers.md) for the Python-specific rules the surveys classify "Py".

Brief: create workflow/packs/python/ following the same layer shape as workflow/base/
(rules/<id>.md, one must/should statement per file, with ids -- see workflow/base/rules/
for the existing pattern and id conventions). Cover, from the two surveys' classification
tables:
- uv as the package manager / `uv run pytest` (data-contracts), **and** pipenv as an
  alternative (`pipenv run pytest`, meta-notes) -- the pack must support both as a tool
  binding, not just uv. Don't build a third option speculatively; two is what's needed.
- ruff for both lint (`ruff check .`) and format (`ruff format .`) (data-contracts).
  meta-notes has no linter/formatter config -- don't force one on it, keep ruff as
  optional/data-contracts-specific if meta-notes' project layer omits it.
- "Test at the supported Python floor" (the pack states the rule; the floor value itself,
  e.g. data-contracts' 3.12 or meta-notes' documented-3.11-but-developed-on-3.14, is a
  per-project setting supplied in each project's own .bridle/ layer -- don't hardcode
  either project's floor into the pack).
- `ruff extend-exclude = ["*.md"]` (or the pack's equivalent guidance) so quoted code
  in prose docs isn't reformatted -- see data-contracts' pyproject.toml and tickets
  at7m/yhgu for why this matters. Applies only where ruff is in use.
- Bare-function pytest style (`test_<module>_<function>_<scenario>`, `tmp_path`, no
  classes -- meta-notes' AGENTS.md) as a pack *option*, not a mandate: data-contracts
  doesn't follow it, so this must be opt-in per project, not a pack-wide must rule.

This task depends on br-4221 (check-command binding) landing first: the pack's own
"how to run check" rule should point at the binding mechanism br-4221 builds, not
hardcode `make check`/`./run_tests.sh && pipenv run pytest`/duplicate the just-check logic.

A project opts in via `.bridle/config.toml`'s `packs = ["python"]` (see
docs/design/workflow-layers.md's example). Don't wire data-contracts' or meta-notes' own
config in this task -- that happens on each project's own side once the pack exists.

Acceptance: just check passes; `bridle rules explain`/`diff` (crates/bridle/src/cli.rs,
commands.rs) picks up the new pack rules when a fixture project lists `packs = ["python"]`
-- add or extend a test fixture if the existing rules tests don't already cover a
non-empty pack; a fixture or test demonstrates both the uv and pipenv binding paths
producing a correct rendered command.

Out of scope: a TypeScript, Vim/vader or other pack (Vim/vader is a separate task, br
pending); data-contracts' or meta-notes' own project-layer config; anything
OpenSpec/spec-pipeline-related (that's P3, not this pack).

Model: Sonnet (new pack content, two tool bindings, plus a fixture/test).
