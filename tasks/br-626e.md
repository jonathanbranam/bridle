Bug: `bridle tui` calls `list_agents` once at startup (`run_app`, crates/bridle-tui/src/run.rs).
After that, `apply_event_to_agents` (crates/bridle-tui/src/app.rs) only updates rows it
already has (`agent.state`) and drops removed ones (`agent.removed`); its doc comment says a
new agent "only shows up on the next full agents list", but nothing lists again. The human
missed a worker spawned while the TUI was open until they restarted it. The TUI is how they
watch the work.

Fix: re-fetch the agents list when an event for an agent with no row arrives (the spawned
event; check the exact event kind name in crates/bridle-api/src/types.rs), and after an SSE
reconnect (events can be missed while disconnected). Keep selection stable across the
refresh (same agent stays selected, index clamped), and don't block the UI loop on the
fetch (follow how run.rs does its other async fetches). Prefer refreshing on the specific
trigger over polling on a timer.

Acceptance: `just check` passes; a test that a spawn event for an unknown agent leads to the
agent appearing (a state/reducer-level test or a run-loop test with the existing test
harness/fake client, whichever the crate already uses), and that selection survives the
refresh.

Out of scope: layout or panel changes (y496), scrolling (done), any other TUI work. Note
crates/bridle-tui is also being edited by br-0e14 (open a message in full; running now):
rebase on main before you start and again before handoff.

Size: small. Model: Sonnet (Haiku is enough if it stays a reducer + one refetch).
