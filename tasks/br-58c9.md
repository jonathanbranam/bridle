First slice of docs/tickets/open/the-orchestrator-watches-the-machine-s-load-and-reacts-to-it-58c9.md (read it; context: load hit 70 on 16 cores from a target-dir copy for a spawn plus syspolicyd/XprotectService scanning new binaries). The ticket gives the ask but no design, so this slice is deliberately small and I assumed the reaction; the worker should confirm against the code first and comment on the thread if it disagrees. Build: (1) the daemon samples the machine load average (libc getloadavg or equivalent, no unsafe: unsafe is forbidden in this workspace, so use sysinfo or read /proc/loadavg / parse sysctl vm.loadavg; pick what the workspace already depends on) on a timer, normalised by core count; (2) bridle status shows it; (3) a configurable threshold ([machine] load_per_core, with a default; absent config keeps working) above which the daemon holds NEW agent spawns (like the budget hold: resume when it falls) and sends the orchestrator a message once per crossing, naming the load and the top consumers if cheap to get; (4) the orchestrator role prompt (workflow/base/roles/) says what to do on that message (do not add work, wait). Files: crates/bridle-daemon (supervisor spawn gate, config), crates/bridle (status), cli.md, the daemon doc, the orchestrator role. Acceptance: just check passes; tests with an injected load source for hold, release and one message per crossing. Model: Sonnet. Out of scope: winding down running agents by project priority and cross-project coordination (design xypj, not scheduled), killing processes, and fixing the cause (the target-dir copy).
