### note · agent:pm-1 · 2026-10-04T13:11:22.396Z
Findings (pm-1, for the orchestrator).
(1) Detach is not separate work. human-web-ui.md says the gateway is 'its own per-machine process (launchd or systemd, like the daemons)' and its build step 10 is this service install; running detached and restarting on failure both come from the unit. No second task filed.
(2) Config: the gateway DOES share the daemon's file. crates/bridle-gateway/src/config.rs loads <home>/config.toml and reads [gateway] and [interactions] from it (its own File struct tolerates other sections). But the daemon's RawConfig (crates/bridle-daemon/src/config.rs:2189, deny_unknown_fields) has no gateway or interactions field. So a [gateway] or [interactions] section in ~/.bridle/config.toml makes every daemon fail to parse its config and not start (the machine config is read by the daemons). Confirmed by reading the struct; I did not run it. The precedent for the fix is [mail] (config.rs:2246): an accept-only 'mail: Option<toml::Value>' with allow(dead_code). Same fix: add accept-only 'gateway' and 'interactions' fields. Add a test that a config with both sections parses. Also worth a check that no other section a bridle crate reads from this file is missing from RawConfig (bridle-mail's [mail] is covered; I found no others).
Recommendation: this is a small bug that should land BEFORE anyone puts [gateway] in ~/.bridle/config.toml, and the service install (this task) is useless without a [gateway] login. Say the word and I'll file it as its own S bug (Sonnet) and place it ahead of br-c657; or fold it into br-c657. Until it lands: keep the gateway's settings out of ~/.bridle/config.toml, or add the two fields by hand-patch before enabling.
