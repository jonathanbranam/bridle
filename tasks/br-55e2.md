§"Bridle side" step 2, go-ahead from the human 2026-09-28: "yes, it's an example of a
different language again, different test framework, etc." -- a Vim/vader pack, not kept
project-local). meta-notes is a Vimscript plugin plus a Python CLI; its Vimscript tests
run through vader.vim.

Brief: create workflow/packs/vim/ following the same layer shape as workflow/base/ and
(once it lands) workflow/packs/python/ (rules/<id>.md, one must/should statement per file
-- see workflow/base/rules/ for the existing pattern and id conventions). Cover, from the
survey's classification table (the "Vim" rows):
- vader.vim as the test framework, run through `./run_tests.sh` with flags
  (`[file] [--quiet|--debug|--interactive]`) -- the runner script itself stays in the
  project (it's meta-notes' own file), the pack states the convention: a clean-runtimepath
  `vim -es` invocation, `$VADER_PATH` pointing at the vader.vim install (default
  `~/.vim/pack/testing/start/vader.vim`), and the temp-dir setup/cleanup pattern used for
  filesystem tests (see MN/AGENTS.md's Vader testing section for the shape; the doc there
  has a known minor bug mixing up `g:test_dir`/`g:test_root` -- don't propagate that
  confusion into the pack, write it correctly).
- "Don't depend on `after/ftplugin/` being in the runtime path" -- a portability rule
  for Vimscript plugin structure (meta-notes' CLAUDE.md has the project-specific mapping
  convention this generalizes from; keep the pack rule general, leave the
  `<localleader>`/`autocmd FileType` specifics as a meta-notes project rule, not a pack
  rule).

This pack's own "how to run check" rule should point at the check-command binding
mechanism br-4221 builds (same pattern as the python pack), not hardcode
`./run_tests.sh && pipenv run pytest test/unit/` (that combined command is meta-notes'
own project-level binding, spanning two packs -- vim and python -- which is fine and
expected).

A project opts in via `.bridle/config.toml`'s `packs = ["vim", "python"]` (see
docs/design/workflow-layers.md's example, and how python's fixture test works once
br-7678 lands).

Acceptance: just check passes; `bridle rules explain`/`diff` picks up the new pack rules
when a fixture project lists `packs = ["vim"]` -- add or extend a test fixture consistent
with however br-7678 tested the python pack.

Out of scope: the vader-adapter for bridle's future spec-to-tests pipeline (P3 input, see
MN/docs/gherkin-compiler-testing.md -- note it as a pointer, don't build it); meta-notes'
own project-layer config; the Python pack itself (br-7678, separate).

Model: Sonnet (new pack content plus a fixture/test, mirrors br-7678's approach).
