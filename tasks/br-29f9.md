GATING: per the human's standing rule (workflow/base/rules/existing-projects.md, locked,
ticket 63rv), no agent works in any other project (data-contracts, meta-notes, track-web,
otters, file-db, ...) until this task lands. Every onboarding is a trial on its own
integration branch; a project's real `main`/`dev` are never touched until the human
reviews and approves adoption. This task is what makes the integration branch a project
setting, which the trial model depends on -- treat it as the single blocker in front of
br-4221/br-7678/br-55e2/br-bc21 and every onboarding task after it.

The human's ask (verbatim, 2026-09-28): "File a ticket to enhance bridle to support strong
rules for branch usage. Some projects work directly on main, others use a dev branch.
KISS, but merging to main for a release is a common enough pattern. don't add complexity
for other approaches." And, on trial adoption (63rv): "the change to control git branches
that manager and workers use must land before this so they can target the bridle main
branch while still making their own worktrees."

Why now: track-web's survey (u8sm) found day-to-day work happens on `dev`, and a push to
`main` deploys to production via a GitHub webhook. Bridle hardcodes `main` in several
places:
- .bridle/roles/manager.md: `git log main..bridle/<name>`, merge into `main`,
  `merge-base --is-ancestor main bridle/<name>`, `git push origin main`, "push anything
  but main" under Never.
- workflow/base/skills/worker/SKILL.md: "merge the local `main` into your branch".
- docs/design/agent-host/operating-model.md: "only the merger pushes, and only `main` and
  release tags".

The worktree base is already configurable (`base` in .bridle/config.toml, default "HEAD",
crates/bridle-daemon/src/config.rs:57/112/137/161) but nothing ties the roles/skills to it.

Scope (the human's: KISS, exactly two patterns, nothing else -- no release branches, no
git-flow, no per-feature integration branches):
1. Trunk: work merges into `main`; releases are tags on `main` (bridle's own pattern today).
2. Dev + release: work merges into `dev` (the integration branch); `main` only moves when
   `dev` is merged into it for a release, done by whoever cuts releases (orchestrator or
   human) -- not by workers or the manager's normal merge.

Brief: add one project setting naming the integration branch (default "main", so bridle's
own project needs no config change) and, for pattern 2, the release branch name. Wire it
through:
- The worktree base (already reads `base` -- check whether "integration branch" and
  "worktree base" should be the same config key or two, and don't introduce two knobs
  if one covers both).
- The manager's merge and push targets (.bridle/roles/manager.md, and wherever the
  manager's actual merge/push logic lives if any of it is in code, not just the prompt --
  check crates/bridle-daemon/src/supervisor.rs and any git-invoking code path used by the
  manager role).
- The worker's handoff merge (workflow/base/skills/worker/SKILL.md).
- A strong (locked, docs/design/workflow-layers.md override semantics) rule that agents
  push only the integration branch and never merge into or push the release branch except
  as the release step. "Strong" means enforced where bridle can (e.g. disallowed_tools on
  git push targets in .bridle/config.toml roles, similar to today's
  `Bash(git push *)` disallow pattern for workers), not only written in a prompt --
  prefer a mechanical check over a written rule wherever bridle already has the hook to
  enforce one.

Trial-onboarding scope (63rv), part of this task, not a follow-up: a trial's integration
branch is a *third* value the same setting must be able to hold -- not "main", not "dev",
but a per-project trial branch name (the setting isn't limited to the string "main"/"dev"
literals; make sure whatever you build takes any branch name). Also handle:
- **Naming collision**: agent branches are `bridle/<agent>`, the state branch is
  `bridle/state`. A trial branch named e.g. `bridle-trial` (not `bridle/main`, which would
  collide with an agent literally named "main") must not collide with an agent branch.
  Check `validate_agent_name` in crates/bridle-daemon/src/worktree.rs -- it doesn't reserve
  "state" today, which is the same class of bug; fix both while you're in there (reserve
  "state" and whatever word the trial-branch convention uses, e.g. "trial", as agent
  names bridle refuses).
- **Where the manager merges during a trial**: the manager merges in the main clone, which
  the human also uses day to day. During a trial the clone would need the trial branch
  checked out instead of the project's real main/dev, or the manager needs to merge
  somewhere else entirely (a second clone/worktree dedicated to the trial). Pick the
  simpler of the two that doesn't disturb the human's own checkout, and document the
  choice -- this doesn't need to be elaborate, just correct and stated.
- Pushing the trial branch to the project's own remote is a separate, human-approved
  decision, out of scope for this task -- don't build push-the-trial-branch-automatically
  behavior, just make sure nothing here pushes `main`/`dev` under any circumstance,
  trial or not.

Acceptance: just check passes; a test that a project configured for pattern 2 (dev +
release) has its manager merge/push target `dev`, not `main`; a test that a project
configured with a trial branch name has the manager/worker target that branch and never
touch `main`/`dev`; a test that `validate_agent_name` refuses "state" and the trial-branch
reserved word; docs/design/agent-host/operating-model.md and roles-and-lifecycle.md
updated to describe both patterns, the trial case, and where the setting lives.

Out of scope: anything beyond the two named patterns plus the trial case; the merge.ff=only
fix (br-544b, separate and already queued); building the release-cut flow itself (who/how
`dev` gets merged into `main` for a release) beyond naming the release branch and keeping
ordinary agents off it; actually onboarding any project (that's the tasks this one gates).

Model: Sonnet (touches role config, enforcement mechanism, worktree naming and docs
together).
