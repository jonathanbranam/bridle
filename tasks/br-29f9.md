The human's ask (verbatim, 2026-09-28): "File a ticket to enhance bridle to support strong
rules for branch usage. Some projects work directly on main, others use a dev branch.
KISS, but merging to main for a release is a common enough pattern. don't add complexity
for other approaches."

Why now: track-web's survey (u8sm) found day-to-day work happens on `dev`, and a push to
`main` deploys to production via a GitHub webhook. Bridle hardcodes `main` in several
places:
- .bridle/roles/manager.md: `git log main..bridle/<name>`, merge into `main`,
  `merge-base --is-ancestor main bridle/<name>`, `git push origin main`, "push anything
  but main" under Never.
- workflow/base/skills/worker/SKILL.md: "merge the local `main` into your branch".
- docs/design/agent-host/operating-model.md: "only the merger pushes, and only `main` and
  release tags".

The worktree base is already configurable (`base` in .bridle/config.toml, default "HEAD",
crates/bridle-daemon/src/config.rs:57/112/137/161) but nothing ties the roles/skills to it.

Scope (the human's: KISS, exactly two patterns, nothing else -- no release branches, no
git-flow, no per-feature integration branches):
1. Trunk: work merges into `main`; releases are tags on `main` (bridle's own pattern today).
2. Dev + release: work merges into `dev` (the integration branch); `main` only moves when
   `dev` is merged into it for a release, done by whoever cuts releases (orchestrator or
   human) -- not by workers or the manager's normal merge.

Brief: add one project setting naming the integration branch (default "main", so bridle's
own project needs no config change) and, for pattern 2, the release branch name. Wire it
through:
- The worktree base (already reads `base` -- check whether "integration branch" and
  "worktree base" should be the same config key or two, and don't introduce two knobs
  if one covers both).
- The manager's merge and push targets (.bridle/roles/manager.md, and wherever the
  manager's actual merge/push logic lives if any of it is in code, not just the prompt --
  check crates/bridle-daemon/src/supervisor.rs and any git-invoking code path used by the
  manager role).
- The worker's handoff merge (workflow/base/skills/worker/SKILL.md).
- A strong (locked, docs/design/workflow-layers.md override semantics) rule that agents
  push only the integration branch and never merge into or push the release branch except
  as the release step. "Strong" means enforced where bridle can (e.g. disallowed_tools on
  git push targets in .bridle/config.toml roles, similar to today's
  `Bash(git push *)` disallow pattern for workers), not only written in a prompt --
  prefer a mechanical check over a written rule wherever bridle already has the hook to
  enforce one.

Acceptance: just check passes; a test that a project configured for pattern 2 (dev +
release) has its manager merge/push target `dev`, not `main`; docs/design/
agent-host/operating-model.md and roles-and-lifecycle.md updated to describe both patterns
and where the setting lives.

Out of scope: anything beyond the two named patterns; the merge.ff=only fix (br-544b,
separate and already queued); building the release-cut flow itself (who/how `dev` gets
merged into `main` for a release) beyond naming the release branch and keeping ordinary
agents off it.

Model: Sonnet (touches role config, enforcement mechanism and docs together).
