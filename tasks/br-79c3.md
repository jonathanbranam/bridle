Goal: a name that equals a role name or starts with "<role>-" is RESERVED and only certain principals may create an agent under it, so `orchestrator` is that role and `advisor-Jim` is definitely an advisor. Any name without a reserved base or prefix stays allowed unless something else restricts it.

Reserved bases: the role names in workflow/base/roles/ (advisor, manager, orchestrator, product-manager, worker) plus the short forms the daemon itself uses (`pm`, as in `pm-1`, and `manager-<n>`). Build the list from the loaded roles plus a small const for the short forms, not a second hand-kept list if avoidable. Match: exact base, or base followed by "-". Case-insensitive.
Who may create a reserved name (the safe default, state it in the docs): the human; the daemon itself (it starts managers and PMs and the on-demand ones: check how it spawns them and keep that working); and for `advisor` / `advisor-*` also the orchestrator. Everyone else (managers spawning workers, workers) gets a clear error: "name <x> is reserved for the <role> role; spawn it as <role>" (or the right principal). Workers named after tasks (send-hint, completions, parses-fast, deny-write...) must keep spawning: add a test that a list of names in real use today (take them from `bridle agents --json` history in a fixture: manager-2, pm-1, task-slug names above, and names like `worker1`) all still spawn, EXCEPT only the deliberately reserved ones.
Resume of an already-existing agent that carries a reserved name is never blocked (grandfathered): a daemon restart must still resume manager-2 and pm-1. Test that.
Also the `send` recipient lookup (the a911 hint) should stay correct; no change needed unless a test shows one.
