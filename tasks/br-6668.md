Why: the human wants to stop running `just check` repeatedly per merge (the orchestrator
already stopped and now reads CI), and the NUC can't take the load. Remote CI is the gate
after the push; nothing currently tells anyone when it goes red. "Just GitHub Actions is the
only thing we need"; "keep it simple". Prioritised by the human.

Build a small poller in the daemon (not an agent, no webhook, no new dependency) using the
`gh` CLI:
- Opt-in per project: `[ci] github = true` in .bridle/config.toml (add to config.rs; note
  deny_unknown_fields). Off by default; without it nothing runs. Don't auto-detect.
- Trigger: when the integration branch's (`[branches] integration`) tip on `origin` changes
  (check `git ls-remote origin <branch>` every few minutes; do not depend on seeing the
  merger's push). For the new sha, run
  `gh run list --commit <sha> --json databaseId,status,conclusion,url,name` (run in the
  main clone with the project's cwd).
- Poll every 1-2 minutes until every run for the sha is `completed`, then stop; give up
  after about an hour. Handle "no runs yet" as keep polling; handle `gh` missing or failing
  as one logged warning, not a crash or a loop of errors.
- Report: emit a `ci.completed` event (sha, conclusion, url) so the watcher/TUI see it. On
  failure, send a bridle note to the manager role (the merger), with the url and the failed
  jobs' names ("CI failed on <sha>: <jobs>; don't merge until it's green"; get job names
  from `gh run view <id> --json jobs` on failure only). Send nothing on success.
- `bridle status` shows the last CI result for the integration branch (sha, conclusion,
  url, age). Add to the status wire type in crates/bridle-api/src/types.rs and all clients
  together.

Look at how the daemon runs background loops (governor/watcher in crates/bridle-daemon/src)
and follow that pattern; put the poller in its own module. Shell out to `gh` through a small
trait or function so tests can inject fake `gh` output; no test may call the real `gh` or
the network.

Acceptance: `just check` passes; tests with faked `gh` output for: success (event, no
message), failure (event + message to the manager naming failed jobs), still-running then
completed, no runs yet, `gh` erroring (one warning, keeps going next tick), disabled by
default (no calls). Docs: docs/design/agent-host/ (the daemon doc that lists its background
loops), docs/design/cli.md for the status output, config documented where `[branches]` is.

Out of scope: webhooks, non-GitHub CI, the paths-ignore workflow change, mt7r/check-affected,
any agent that fixes failures.

Model: Sonnet. Touches config.rs and types.rs like other tasks, but they're small edits.
