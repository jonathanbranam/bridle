HARD CONSTRAINT (every agent resolves tokens through this path): today's resolution order and results must not change for any existing setup. Add the new lookup ONLY as the last step, in the case that today ends in the error "no workspace found to read the human token from" (or the human token file is absent): then, and only then, try [human.<machine>] for the target daemon's machine. Do not reorder --token, $BRIDLE_TOKEN, $BRIDLE_AS, the workspace token file. Keep the error, extended to name credentials.toml [human.<machine>] as the fix.
First, check (with a test) whether BRIDLE_AS=human plus [human.dalek] already works today; if so, the fallback just makes it automatic.
Tests: unit tests in discovery.rs for the unchanged order (each existing case: flag, env, AS entry, workspace file, same-machine) AND the new fallback (found; missing -> the improved error); a local-machine project still uses the workspace token file even if [human.*] exists.
Docs: principals.md and cli.md token rule; CHANGELOG. Acceptance: just check passes.
Model: Sonnet. Out of scope: copying tokens, a command to set them up (sk7p builds on this), any other principal.
