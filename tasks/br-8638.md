PM manages the queue in bridle task (planned/ready/claimed, plus an order); manager takes from bridle ready; the human can query current and next-up tasks. No briefs by message (human, 2026-09-28).

Brief:

1. Add the missing open -> planned transition. Today nothing produces the initial `planned` state: TaskManager (crates/bridle-daemon/src/tasks.rs) only reaches `Planned` via release_claim() reverting from `Claimed` (claim_task at line 615 requires the task already be Planned, line 427). Add a `plan_task(id, actor)` (open -> planned; TaskError::Conflict if not currently open), a POST /v1/tasks/{id}/plan endpoint (server.rs, alongside claim/release/drop/reopen), and `bridle task plan <id>` in the CLI (crates/bridle/src/cli.rs, commands.rs). This is the PM-only action that puts a task in bridle ready.

2. Add an order/rank among ready tasks, set by the PM, so "next up" is a query not a message. Simplest: an integer `rank` column on `tasks` (docs/design/storage.md schema, migration in store.rs), settable via `bridle task plan <id> --rank N` (or a separate `bridle task rank <id> N`), nullable/default so existing tasks are unaffected; `bridle ready` sorts ascending by rank (nulls/ties last, then created_at). Mirror the field into the state-branch task file frontmatter (state_branch.rs) alongside the existing fields.

3. One queue view for the human: `bridle queue` (or `bridle task list --queue`) showing claimed tasks with their worker (claimed_by), then ready tasks in rank order. Read-only, reuses TaskManager::list_tasks/claims.

4. Update both role prompts to stop the message-based flow: `.bridle/roles/product-manager.md` (remove the "Keep the development manager's queue full... Send it prepared tasks" instruction; replace with: write briefs into task bodies via `bridle task edit`, `bridle task plan` to make them ready, `bridle dep add` for `blocks` edges where order matters, and send the manager only a short nudge that the queue changed) and `.bridle/roles/manager.md` (take work from `bridle ready`, claim it, spawn workers from the claimed task's body instead of waiting for a "Prepared task" message).

5. Update docs/design/agent-host/roles-and-lifecycle.md and storage.md for the new transition, rank field and queue view.

Acceptance: just check passes; tests for plan_task's state transition and conflict cases, rank ordering in bridle ready/queue, and that an already-planned/claimed/dropped task cannot be re-planned. If this is too much for one context window, it is fine to land the plan-transition + rank as one PR and the queue view + role-prompt docs as a second, in that order, on top of each other.

Out of scope: in_review/integrated/accepted states and the state-branch work for them (still open, c7eb) -- this only needs open/planned/claimed/dropped/reopened, already built.
