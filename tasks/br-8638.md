The model (human-agreed, see ticket "The model" section):

- Tasks stay the what: brief in the body, kind, real `blocks` edges only for actual dependencies -- no ordering on the task, no edges used to force an order.
- The queue is a separate record the PM owns: an ordered list of tiers, each tier a set of equally-ranked task IDs; tier 1 before tier 2. A task not in the queue is backlog.
- The development manager is mechanical: takes from the highest tier with a startable task (deps met, unclaimed), picks within a tier by load/free worker slots (model size; tasks touching the same files run one after another). Never moves tasks between tiers; if a tier is stuck on dependencies, takes from the next tier instead of idling.
- Durable: queue lives on the state branch beside tasks (bridle rebuild restores it; every reprioritisation is a commit). Claims should also become durable (today SQLite-only, storage.md "claims" -- a rebuild currently forgets who is working what).
- Visible: `bridle queue` shows tasks being worked (with worker), then the tiers in order.
- Only the PM (and the human, to override) edits the queue; the manager only reads and claims.

Brief:

1. Add the open -> planned transition. Today nothing produces it: TaskManager (crates/bridle-daemon/src/tasks.rs) only reaches `Planned` via release_claim() reverting from `Claimed` (claim_task at line 615 requires the task already be Planned, line 427). Add `plan_task(id, actor)` (open -> planned), a POST /v1/tasks/{id}/plan endpoint, and `bridle task plan <id>` in the CLI.

2. Add the queue record: an ordered list of tiers of task ids, separate from `tasks`/`edges`. Persist it on the state branch (state_branch.rs) alongside task files, e.g. `queue.md` or `queue.toml` with an ordered list of tier -> [task ids], so `bridle rebuild` restores it and every edit is a commit with an actor. PM-only write path (`bridle queue set`/`bridle queue add-tier`/similar -- pick the smallest surface that covers reorder, add, remove); `bridle ready` and `bridle queue` read it to pick/display the highest startable tier.

3. Durable claims: today `claims(task_id, claimed_by, claimed_at)` is SQLite-only and never mirrored to the state branch (storage.md, "claims"), so a rebuild forgets who is working what. Mirror claim/release to the state branch the same way task state changes are (state_branch.rs), so `bridle rebuild` restores current claims too.

4. `bridle queue`: one read-only view -- claimed tasks with their worker (claimed_by), then the tiers in rank order, each showing its task ids/titles and which are startable (deps met, unclaimed) vs blocked.
