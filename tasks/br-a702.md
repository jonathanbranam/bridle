The human's ask (verbatim, 2026-09-28): track-web has one backend shared by many clients
(client-games, client-trips, client-watch, client-play, ...), each with its own local
conventions, roadmap, planning and tickets. client-games itself has sub-projects
(dungeon-tactics, space-golf, ball-merge) that are components nested under it. "Work
should be coordinated and managed together in a single bridle, but needs to be clear
which project is being worked on so any project-local rules can be applied." In
particular: an agent planning tickets/proposals with the human should only need context
for the server, its client-*, and its sub-project.

Gaps to resolve in the design (advisor's reading, ticket's "Gaps" section):
1. Scope by the task/spawn, not cwd -- spike 06 (docs/spikes/06-path-scoped-rules-findings.md)
   shows nested CLAUDE.md loads by cwd, which fits a worker inside one client's directory
   tree but not a planning/proposal agent working with the human outside any single
   client's path. The task or spawn needs to name its component(s), and `bridle prime`
   needs to hand the agent L3 (project) plus the named client plus the named
   sub-project/game.
2. Nested components: a game is a component whose paths sit under its client's paths and
   inherits the client's rules -- confirm the layer-resolution model (rules.rs resolve())
   already composes this correctly for a 2-deep nesting, or note what it needs.
3. Components carry more than rules: roadmap, planning, tickets, and "who this is for and
   why". Task lists need to filter by component. Scope how much of this the design
   proposes building now vs. deferring.
4. Spike 06's render target (.bridle/components/<n>/CLAUDE.md) wouldn't be loaded by cwd
   since it isn't under the component's own path tree. Claude Code's .claude/rules/*.md
   with `paths:` frontmatter is unverified by the spike -- if this design step needs that
   verified, that's a small follow-up spike, not something to guess at here.
5. Anything actually rendered into track-web falls under 63rv (the bridle-adopt trial
   branch, human review) -- this design task doesn't touch track-web itself.

Human's answers already settle some of this (2026-09-28, don't re-litigate):
- Games as components nested in client-games: yes.
- Restriction is soft, not hard (clients/games can share approaches; agents may still see
  sibling context, just aren't required to).
- Roadmap/planning/ticket location: unsettled -- "I'm not sure where roadmaps live... I
  want to be able to review them myself fairly easily as markdown files." Related open
  question hv8e. This design task should propose an answer consistent with "easy to
  review as markdown," not invent a new storage format.
- Every track-web task names its component(s) as a soft rule; a task may span components
  (a list) or be repo-wide.

Brief: produce a short design doc (docs/design/ or a ticket-linked note, your call on the
best home given bridle's existing docs/design/ conventions) that: names the component
model for nested components (client → sub-project), proposes how a task/spawn declares
its component(s) and how `bridle prime`/`bridle sync` scope context to L3 + named
components, proposes where roadmap/planning/ticket content per component lives
(answering or at least narrowing hv8e), and states what's deferred vs. what a follow-up
implementation task should build. This task's acceptance is the design landing and being
reviewable, not code -- implementation is separate future task(s) this one should
identify.
