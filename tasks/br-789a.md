Found by manager-2 (m-1000, 2026-09-28) while claiming br-7678: it has a blocks-edge on
br-4221. br-4221's code had already merged to main (b5750d2), but blocker_is_resolved
(crates/bridle-daemon/src/tasks.rs:479) only treats a blocker as resolved when its state
is Dropped -- there's no done/integrated/accepted state yet (bridle task --help: "Scoped
for now to open/planned/dropped/reopened; claimed/in_review/integrated/accepted arrive
with later tasks"). So a genuinely-finished-and-merged blocker task stays 'planned'
forever and its blocks-edges never clear on their own; today's workaround is the PM
manually dropping the finished task with a reason noting the merge commit, which is a
misuse of 'drop' (meant for abandoned work, not completed work) and easy to forget.

Brief: once in_review/integrated/accepted land (br-8638's follow-up scope, or whichever
task adds them), make blocker_is_resolved also treat a blocker in a terminal
completed state (integrated/accepted, whatever the final name is) as resolved, not only
Dropped. If those states are still far off, a smaller interim fix is acceptable: judge
what's proportionate when you pick this up.

Acceptance: just check passes; a test that a blocks-edge clears once the blocker reaches
its terminal completed state, not just when dropped.

Out of scope: designing in_review/integrated/accepted themselves (tracked elsewhere,
this task only wires blocker_is_resolved to whatever lands).

Model: Haiku or Sonnet depending on how much of the target state machine exists when
this is picked up -- judge at pickup time.
