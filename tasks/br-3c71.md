Ticket: docs/tickets/open/a-settle-period-an-approved-task-waits-a-few-minutes-before-ny9u.md (read it all: the human's words, the advisor's notes, and 'Decided'). Design docs: docs/design/storage.md and docs/design/coordination.md (task lifecycle, ready/queue/claim), roles-and-config.md (config). Code: the task readiness logic behind 'bridle task ready', 'bridle task queue' and 'claim' in crates/bridle-daemon, 'task show' output in crates/bridle, the task thread and event code, daemon config.

Goal: every task settles for a short period before anyone can start it; the daemon enforces it.
DESIGN, KISS, NO SCHEMA CHANGE: settled_at is computed, not stored: settled_at = max(task created_at, time of the latest human comment, human edit or human question/answer in the thread) + settle period, unless a settle-skip note is in the thread. So existing tasks need no migration (anything older than the period is already settled) and nothing new can break daemon start-up or state-branch rebuild. If a human edit of title/body is not yet recorded in the thread, make it record a note (kind note, from the human principal) so the clock can see it.
1. Config: '[tasks] settle = "5m"' (duration, same parser as other durations; default 5m; "0" or 0 turns it off). Per project in .bridle/config.toml. Invalid value: a clear config error naming the key, but see SAFETY.
2. Startable means: planned, deps satisfied, AND settled. 'task ready', the queue's startable flag, and 'claim' all refuse an unsettled task with 'settling until <time ET>' (the human's times are US Eastern; see workflow/base/rules/human-timezone.md for how others format it). The PM can still PLAN an unsettled task; claims by the human on their own to-dos (created already claimed, --for-human) are exempt.
3. Show it: 'task show' and 'task queue' print 'settling until 10:42 AM' (ET) for a task still settling, and JSON gets a settle_until field (null when settled).
4. Skips, recorded: 'bridle task skip-settle <id> --reason "..."' appends a thread note (who, why, when; event task.settle_skipped) and the task counts as settled. Allowed for the human, and for the orchestrator or PM only with a reason, which must say it is because the human asked or because of an urgent downtime fix (free text, but required and recorded). No other principal.
5. Not an approval gate: nothing waits for a second approval; a project that wants a hard gate keeps using the existing required-human-approval mechanism (do not touch it).
6. Docs: storage.md/coordination.md (lifecycle: settling), cli.md, roles-and-config.md ([tasks] settle), the PM/orchestrator/manager role text only where it says to start tasks immediately (one line: a task settles ~5 min after creation or a human edit; use 'task ready'), CHANGELOG.
Tests (fake or injected clock): a new task is not ready until the period passes, then is; a human comment restarts it; an agent comment doesn't; skip-settle by an unauthorized principal is refused, by the human or a reasoned orchestrator works and is recorded; settle=0 disables it; existing old tasks (created long ago) are startable immediately; claim refuses while settling; human to-do claimed at creation unaffected; JSON field and ET text in show/queue.
SAFETY (the human is away): an invalid [tasks] settle must NOT stop the daemon starting: warn and fall back to 5m (and 'bridle doctor' reports it). No new DB column or table. Do not touch daemon start-up, restart/upgrade or the orchestrator path. Lands normally.
Acceptance: just check passes. Model: Sonnet. Migration plan: none needed; the period is computed from existing created_at and thread data, so old tasks are settled and no project file changes. Out of scope: a hard-approval-gate feature, per-task custom periods, per-role periods.
