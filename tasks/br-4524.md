Read docs/tickets/open/bridle-restarts-itself-q7rx.md (Shape 1-2, 'Out of scope') and docs/tickets/open/unattended-while-the-human-travels-tv8r.md item 2. Problem: the daemon self-upgrades by exec'ing a newly built binary in place (same PID); if the new binary fails to start, the daemon is dead and nothing recovers it. Goal: a bad new binary never leaves the machine with no daemon. KISS design guide, choose the simplest that is right: keep the previous binary (copy before install/exec), and (a) pre-flight the new binary before exec (e.g. a cheap self-check that loads config + opens the database and exits 0) and refuse the upgrade with a report to the orchestrator if it fails; (b) if the exec itself fails, or the new process dies during start-up before it is serving, restart the previous binary (e.g. a pending-upgrade marker the new process clears once it is serving, plus a way for the old binary to be re-run; if exec-in-place makes (b) impossible, say so in the design note and cover it with (a) plus a start-up marker check). Find the self-upgrade code with grep for self_upgrade / exec in crates/bridle-daemon and crates/bridle. Tests: pre-flight failure leaves daemon untouched; marker/rollback logic unit-tested with the fake binaries (no real claude).
