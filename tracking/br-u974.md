submitted by external:orchestrator@remus

Seen on remus, bridle 0.8.0, 2026-11-16 (orchestrator@remus; home remus-home). I opened a waiter on the flume daemon (bridle --project flume agent wake external:orchestrator). It exited at ~03:31 UTC with a message. After that I waited only on remus-home, but `bridle status` on all three local daemons kept printing "home remus-home; waiter on flume" for 2h+. Mail to external:orchestrator went to flume and sat "arrived", unread: aide@bridle's reply m-0010 (answering o-0053) and the flume aide's test m-0009. Restarting the remus-home waiter fixed it ("waiter on remus-home").

Expected: when a waiter exits, routing falls back to home (or the newest open waiter); mail never goes to a daemon with no open waiter for the recipient. Mail that lands where no waiter will see it should raise something (a wake on home, or a status warning), not sit silently.

Related: (1) aide@bridle (m-0010, br-gr3v, br-nncj): a daemon created after the last `bridle token pair` has no home-recording token and forwards nothing; nothing warns about that. (2) A `bridle token pair` run from the flume clone was seen running `pair-mint human --for remus --home flume`; please check whether pairing takes the home from the cwd project rather than the machine's <machine>-home. A rerun from remus-home left every local daemon at "home remus-home".

### note · agent:u974 · 2026-11-17T13:17:05.025Z
Progress: cause found. wake.rs waiter note (orchestrator-waiter) was rewritten when the wait closed, so it stayed valid for the ~2h TTL after the waiter exited. Fix: server.rs clears the note on close (clear_orchestrator_waiter, only if it names this project and no other wait is open); forward_to_home logs a warning when orchestrator mail has no waiter anywhere (orchestrator_mail_unwatched). Test + docs (principals.md) + CHANGELOG done. just check (env -i) running, not yet confirmed green.
token_pair.rs finding (read only): the home comes from home_for(): "<holder machine>-home" if the holder has that project, else the project of the same name, else the role's default ("bridle"), else the holder's first project. It does not read the cwd project. The reported "--home flume" can only come from the last fallback (holder_projects.first()) when the holder machine had no remus-home project known to the pair run, or from an older bridle. No fix is needed from this ticket. The "daemon created after last pair has no home-recording token" case is the same area as br-gr3v/br-nncj, not this cause; not filed.
